# ADR-001: Fundamental Architecture Decisions for Pathways

- **Status**: ACCEPTED
- **Date**: 2026-10-26
- **Context**: Replacing Career Trajectory with Pathways (`PATHWAYS_NAME`) for Indian engineering students and freshers.
- **Governed By**: `docs/pathways/CONSTITUTION.md`

---

## Decision 1: Ledger-First Fact Verification vs. Crowdsourced / Dynamic Scraping

### Context & Problem
Early-career campus hiring in India is riddled with conflicting criteria, unverified salary claims, and opaque selection funnels. Traditional platforms rely on unverified employee reviews (Glassdoor, AmbitionBox) or student forum rumors, creating false expectations.

### Decision
We adopt a **strictly verifiable evidence-ledger pipeline**:
1. Facts are entered **only** as individual immutable ledger rows (`docs/pathways/ledger/*.json`).
2. Every fact must carry an exact quote (at most 15 words) found verbatim in the cached official page (`.evidence-cache/`).
3. Sourced only from official company portals or government statutory portals (`incometax.gov.in`, `epfindia.gov.in`, `labour.gov.in`).
4. Code artifacts (`*.generated.ts`) are generated only by `npm run pathways:build` and protected by SHA-256 content hashes.

### Alternatives Considered & Rejected
- **Alternative 1A: Dynamic Runtime Web Scraping.**
  * *Rejected because*: Violates Constitution Rule B5 (Zero runtime network egress), creates fragile external dependencies, introduces latency on mobile devices, and violates site terms of service.
- **Alternative 1B: Aggregator Data (AmbitionBox, Glassdoor, PrepInsta).**
  * *Rejected because*: Violates Constitution Rule H5 (Strict source allowlist). Aggregators mix lateral salaries with fresher packages and often publish outdated or unverified criteria.
- **Alternative 1C: Peer/Category Imputation.**
  * *Rejected because*: Violates Constitution Rule H8. Missing facts must be recorded as `not_published`, never guessed from industry peers.

## Decision 2: Pure Deterministic Offline Engines vs. Cloud Backend / AI Generation

### Context & Problem
Students need immediate answers without uploading sensitive academic transcripts, backlogs, or confidential offer letters to remote servers. Furthermore, calculation results must be strictly repeatable across audits.

### Decision
All computation (Eligibility Radar, CGPA Gap Calculator, Action Plan, Offer Evaluator) runs as **pure deterministic functions** in the browser:
1. No `Date.now()`, no `Math.random()`. The reference date `asOf` is injected explicitly.
2. Every output carries a comprehensive **Trace** documenting inputs used, rules applied, evidence references, and draft/reviewed assumptions.
3. All student scenarios are persisted locally in browser localStorage under dedicated keys (`hireflow:v4:pathways:*`).
4. Internal monetary amounts are integer rupees, with half-up display rounding documented.

### Alternatives Considered & Rejected
- **Alternative 2A: Cloud Backend / User Accounts.**
  * *Rejected because*: Violates student privacy, requires authentication infrastructure, introduces cloud hosting costs, and slows down time-to-first-result.
- **Alternative 2B: LLM-Driven Dynamic Evaluation at Runtime.**
  * *Rejected because*: LLM evaluation is non-deterministic, hallucinates numerical cutoff values, cannot guarantee statutory tax compliance, and requires runtime API network egress.

## Decision 3: 3-Input Instant Budget with Live-Calculated Upgrades vs. Comprehensive Upfront Wizard

### Context & Problem
Mobile users on 390px screens have short attention spans. Demanding 10+ academic fields (10th, 12th, diploma, CGPA, semester, backlogs, gaps, degrees) before showing any results causes high bounce rates. Conversely, hiding necessary criteria produces misleading "eligible" badges.

### Decision
We implement a **3-Input Initial Budget** with live-calculated upgrades (Constitution Rule E8):
1. **Initial Screen**: Only Branch, Batch Year, and CGPA are required to render instant results across 4 distinct buckets (`Meets`, `Check`, `Fails`, `Unknown`).
2. Programs requiring unprovided criteria are placed in `Check these details`, accompanied by explicit `blockingInputs`.
3. An upgrade callout is rendered whose count is computed live from the engine: e.g., *"Add 12th % to settle 6 programs at Check"*.
4. Missing facts remain `unknown` and are never defaulted to a pass (Rule E3).

### Alternatives Considered & Rejected
- **Alternative 3A: Comprehensive Multi-Step Form Wizard.**
  * *Rejected because*: High friction; forces students with incomplete knowledge (e.g. exact 10th percentage) to abandon the tool.
- **Alternative 3B: Optimistic Passing Defaults.**
  * *Rejected because*: Dangerously misleading. Assuming a student passes unentered cutoffs causes heartbreak when students are disqualified at campus placement gates.
- **Alternative 3C: Hardcoded "Upgrade to Unlock" Marketing Copy.**
  * *Rejected because*: Static marketing copy (e.g. "Add more info to get better results") is vague and dishonest. The engine must compute the exact number of programs settled live.

PROBLEM STATEMENT
----------------------------------------
GitHub Actions, Jenkins, and CircleCI are all custom-built CI/CD systems. Understanding how they work requires building one: a master controller that receives webhook events, queues build jobs, distributes them to worker agents, streams build logs, and reports status back to GitHub.

USE CASES IN THE REAL WORLD
----------------------------------------
Self-hosted CI/CD is common in air-gapped environments (defense, banking) and companies with custom build requirements. Understanding CI/CD internals enables optimization of existing systems and contribution to open-source CI tools like Drone, Woodpecker CI, and Concourse.

WHY THIS IS HARD (COMPETENCY REDUCER)
----------------------------------------
CI/CD systems require solving distributed job scheduling, build log streaming, GitHub webhook integration, Docker build isolation, and worker lifecycle management — a rich distributed systems exercise. Engineers who understand CI/CD internals can optimize build pipelines for speed, cost, and reliability.

RECRUITER SHORTLIST SIGNAL

ARCHITECTURE & DATA FLOW
----------------------------------------
Go controller receiving GitHub webhook on push events. Build queue storing pending jobs in PostgreSQL. Docker container-based agents pulling jobs from queue, executing build steps in isolated containers, streaming stdout via WebSocket to controller. Status check API reporting pass/fail to GitHub Checks API.

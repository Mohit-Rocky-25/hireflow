PROBLEM STATEMENT
----------------------------------------
Consuming public or internal REST APIs without typed client libraries forces developers to manually write repetitive, error-prone HTTP boilerplate, maintain fragile interface declarations, and handle intermittent network failures independently. When backend API schemas evolve, unsynced client code fails at runtime rather than compile time. This project builds a code-generation pipeline and runtime SDK engine that parses OpenAPI 3.0/3.1 specifications into strongly-typed TypeScript client packages, featuring automated request authentication, exponential retry logic with jitter, local sandbox mocking, and dual CJS/ESM distribution bundles.

USE CASES IN THE REAL WORLD
----------------------------------------
Public developer platforms and enterprise SaaS organizations publish official, auto-updated client libraries to streamline third-party developer integration. Neutral architectural reference points include open-source SDK toolchains such as Fern, OpenAPI Generator TypeScript, and Hey API.

WHY THIS IS HARD (COMPETENCY REDUCER)
----------------------------------------
Engineering a high-quality client SDK requires solving three nuanced library design challenges:
1. Polymorphic Schema Normalization: OpenAPI specs frequently employ structural composition (`oneOf`, `anyOf`, `allOf`). The code generator must resolve circular `$ref` references and translate complex discriminator properties into idiomatic TypeScript discriminated unions without falling back to loose `any` or `Record<string, unknown>` escapes.
2. Resilient Retries Without Thundering Herds: Naive retry loops compound upstream outages during rate limits (HTTP 429) or transient server errors (HTTP 503). The SDK runtime must implement exponential backoff with randomized decorrelated jitter and automatically inject `Idempotency-Key` headers on mutating requests (`POST`, `PATCH`) to prevent duplicate transactions.
3. Dual-Package Hazard Resolution: To ensure seamless integration across both legacy CommonJS (Node.js) and modern ECMAScript Module (ESM) environments (Vite, Next.js, Bun), the package configuration must strictly adhere to Node.js conditional export maps (`exports` field with distinct `.cjs`, `.mjs`, and `.d.ts` entry points).

ARCHITECTURE & DATA FLOW
----------------------------------------
1. Specification Ingestion: The generator CLI reads an OpenAPI 3.0/3.1 JSON or YAML specification and validates structural compliance.
2. Schema Normalization & AST Generation: The engine resolves internal and external `$ref` pointers, constructs an intermediate Abstract Syntax Tree (AST), and generates strongly-typed request params, response interfaces, and client endpoint methods with JSDoc annotations.
3. Client Runtime Core: A lightweight, dependency-free HTTP client wraps the native `fetch` API, providing configurable base URLs, default headers, and token/API-key authentication middleware.
4. Resilience Pipeline: Middleware intercepts outbound requests: attaches unique `Idempotency-Key` headers, captures HTTP 429/503 responses, respects `Retry-After` headers, and executes exponential backoff with full jitter up to a configurable max attempt count.
5. Sandbox Mock Layer: A runtime flag (`sandbox: true`) routes requests to an in-memory mock handler, returning schema-compliant fixtures generated directly from OpenAPI response examples without making external network calls.
6. Build & Packaging: `tsup` bundles the generated code into tree-shakeable CJS and ESM modules alongside generated `.d.ts` declaration maps.

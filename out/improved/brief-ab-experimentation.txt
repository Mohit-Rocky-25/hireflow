PROBLEM STATEMENT
----------------------------------------
Fixed-horizon frequentist A/B testing requires accumulating a predetermined sample size before evaluating outcomes, which prolongs exposure to suboptimal variants and encourages premature stopping errors (peeking). When teams inspect p-values continuously without formal alpha-spending adjustments, false positive rates escalate significantly. A Bayesian experimentation engine addresses this by maintaining continuous posterior probability distributions over conversion rates, calculating the exact probability that a candidate variant outperforms the baseline and quantifying the expected financial or metric loss of selecting that variant, enabling automated stopping decisions while bounding decision risk.

USE CASES IN THE REAL WORLD
----------------------------------------
Online experimentation platforms evaluate user interface changes, pricing tiers, and checkout workflow variants across high-traffic digital applications. Neutral architectural reference points include web and mobile experimentation platforms such as Optimizely, Statsig, and GrowthBook.

WHY THIS IS HARD (COMPETENCY REDUCER)
----------------------------------------
Implementing a robust Bayesian engine requires addressing three non-trivial mathematical and systems engineering challenges:
1. Preventing False Positive Inflation Under Continuous Inspection: While Bayesian updating is logically coherent under sequential data arrivals, naive early stopping on uncalibrated thresholds ($P(B > A) > 0.95$) during low-sample cold starts ($N < 200$) causes severe discovery bias. The engine must enforce minimum statistical power thresholds and compute Expected Loss thresholds ($\epsilon$) rather than relying purely on tail probabilities.
2. Computational Efficiency vs. Numerical Precision: Simulating $10^5$ Monte Carlo draws per conversion event degrades throughput. The engine must utilize exact analytical formulas or fast numerical quadrature (Gauss-Legendre) for two-variant Beta-Binomial conjugate pairs, reserving numerical simulation for multi-variant comparisons.
3. Concurrent State Ingestion: High-frequency conversion webhooks cause write contention on shared experiment records. The data pipeline must process event increments without deadlocking database transactions.

ARCHITECTURE & DATA FLOW
----------------------------------------
1. Configuration & Initialization: Experiment definitions (variants, prior parameters $\alpha_0, \beta_0$, minimum sample threshold $N_{\min}$, and loss threshold $\epsilon$) are registered via FastAPI and stored in PostgreSQL.
2. Ingestion Pipeline: Conversion events ($(\text{experiment\_id}, \text{variant\_id}, \text{converted} \in \{0, 1\})$) arrive via HTTP POST. Events are persisted to an append-only log table and aggregated into running successes ($k$) and trials ($n$).
3. Bayesian Inference Engine: For each variant, the conjugate posterior $\text{Beta}(\alpha_0 + k, \beta_0 + n - k)$ is calculated. For two-arm tests, $P(B > A)$ is evaluated using numerical integration of the joint distribution.
4. Risk Quantification: The engine calculates the Expected Loss:
   $$\mathbb{E}[\text{Loss} \mid \text{choose } B] = \int_0^1 \int_0^1 \max(0, \lambda_A - \lambda_B) f(\lambda_A) f(\lambda_B) \, d\lambda_A \, d\lambda_B$$
5. Decision Boundary: When $n_A, n_B \ge N_{\min}$ and Expected Loss $< \epsilon$, the engine transitions the experiment state to `STOPPED_WINNER` or `STOPPED_INCONCLUSIVE`.
6. Query Interface: REST endpoints expose real-time posterior parameters, credible intervals ($95\%$), probability of superiority, and stopping recommendations.

PROBLEM STATEMENT
----------------------------------------
SaaS telemetry platforms process millions of interaction events daily from web and mobile clients, but querying aggregate funnel conversions, retention cohorts, and time-series metrics on traditional row-oriented OLTP databases results in excessive query latency and timeouts once tables exceed tens of millions of rows. Analytical systems require columnar storage, data compression, and partitioned indexing to scan billions of values per second. This project builds a multi-tenant telemetry ingestion and analytical engine that streams event beacons through Kafka into a partitioned ClickHouse cluster, maintaining sub-second aggregation latencies across multi-million row datasets.

USE CASES IN THE REAL WORLD
----------------------------------------
Product telemetry systems ingest user interaction streams to generate operational dashboards, conversion funnels, and retention matrices. Neutral architectural reference points include open-source and commercial product analytics systems such as PostHog, Mixpanel, and Amplitude.

WHY THIS IS HARD (COMPETENCY REDUCER)
----------------------------------------
Preventing Part Explosion: ClickHouse creates immutable physical directory parts for every write transaction. Ingesting high-frequency single records directly triggers the 'Too many parts in all data in table' exception, halting ingestion. The pipeline must enforce batch buffering (minimum 10,000 events or 5-second flushes) before persisting to disk. Additionally, multi-tenant queries require strict composite primary key ordering `ORDER BY (tenant_id, event_date, event_name, user_id)` to avoid full table scans across unrelated tenants.

ARCHITECTURE & DATA FLOW
----------------------------------------
1. Ingestion Gateway: A Node.js/TypeScript HTTP service receives JSON beacons, validates payloads against strict JSON schemas, and publishes messages to partitioned Kafka topics keyed by `tenant_id`.
2. Streaming Pipeline: Kafka topics distribute incoming traffic across partitions. A consumer worker buffers messages in memory up to 10,000 records or a 5-second timeout, then executes a single columnar batch insert into ClickHouse.
3. Storage Layer: ClickHouse stores data in a `ReplacingMergeTree` table partitioned by `toDate(timestamp)` with ZSTD column compression. Materialized views pre-aggregate daily active metrics per tenant.
4. Analytical API: REST endpoints execute ClickHouse analytical queries utilizing specialized aggregators like `windowFunnel` for multi-step conversion drop-offs and cohort retention matrices.

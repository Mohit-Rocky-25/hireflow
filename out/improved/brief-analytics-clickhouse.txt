PROBLEM STATEMENT
----------------------------------------
SaaS telemetry platforms process millions of interaction events daily from web and mobile clients, but querying aggregate funnel conversions, retention cohorts, and time-series metrics on traditional row-oriented OLTP databases results in excessive query latency and timeouts once tables exceed tens of millions of rows. Analytical systems require columnar storage, data compression, and partitioned indexing to scan billions of values per second. This project builds a multi-tenant telemetry ingestion and analytical engine that streams event beacons through Kafka into a partitioned ClickHouse cluster, maintaining sub-second aggregation latencies across multi-million row datasets.

USE CASES IN THE REAL WORLD
----------------------------------------
Product analytics platforms ingest high-throughput user clickstreams to generate real-time behavioral metrics. Neutral architectural reference points include open-source and commercial product analytics systems such as PostHog, Mixpanel, and Amplitude.

WHY THIS IS HARD (COMPETENCY REDUCER)
----------------------------------------
Implementing a robust ClickHouse analytical pipeline involves three critical systems challenges:
1. Preventing Part Explosion: ClickHouse creates immutable physical directory parts for every write transaction. Ingesting high-frequency single records directly triggers the `Too many parts in all data in table` exception. The ingestion pipeline must enforce batch buffering (e.g., minimum 10,000 events or 5-second flushes) before persisting to disk.
2. Multi-Tenant Sort Key Design: To ensure fast per-customer queries without full-table scans, the MergeTree primary ordering tuple must lead with tenant isolation keys (`ORDER BY (tenant_id, toDate(timestamp), event_name, user_id)`), balancing tenant data locality with compression efficiency.
3. Complex Funnel and Cohort Aggregation: Writing standard SQL joins over millions of telemetry rows is inefficient; the query layer must leverage specialized ClickHouse aggregate functions (such as `windowFunnel` and `retention`) to compute multi-step user conversions in a single pass.

ARCHITECTURE & DATA FLOW
----------------------------------------
1. Ingestion Layer: A lightweight Node.js/TypeScript HTTP service receives JSON telemetry beacons from client applications, validates payload structure against a strict schema, and publishes messages to partitioned Kafka topics keyed by `tenant_id`.
2. Streaming Decoupling: Kafka buffers event spikes and guarantees at-least-once message delivery.
3. Batch Persister / Kafka Engine: ClickHouse consumes events from Kafka topics via a Kafka Engine table and flushes columnar batches into an underlying `ReplacingMergeTree` table via Materialized Views, buffering in blocks of 10,000+ records.
4. Storage Layer: The primary `events` table uses `ORDER BY (tenant_id, toDate(timestamp), event_name, user_id)` with `ZSTD` column compression.
5. Query Service: A REST/query interface executes analytical queries (funnel conversions, 30-day cohort retention matrix, and time-bucketed event counts) against ClickHouse and returns JSON results to client dashboards.

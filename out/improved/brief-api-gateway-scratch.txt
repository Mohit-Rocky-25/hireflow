PROBLEM STATEMENT
----------------------------------------
Microservice architectures require centralized ingress points to manage cross-cutting networking concerns—such as TLS termination, request authentication, rate limiting, and dynamic traffic routing—without duplicating logic across individual backend services. In horizontally-scaled environments, an ingress gateway must maintain low proxy overhead, support hot-reloading of routing rules without connection drops, balance traffic across upstream replicas using health checks, and execute extensible middleware plugins without introducing unbounded memory allocations or TCP socket leaks.

USE CASES IN THE REAL WORLD
----------------------------------------
Modern cloud platforms and Kubernetes clusters rely on edge gateways to safely expose internal services to external clients. Neutral architectural reference points include open-source gateways such as Envoy, Apache APISIX, and Traefik.

WHY THIS IS HARD (COMPETENCY REDUCER)
----------------------------------------
Building a performant, extensible gateway in Go presents three formidable systems challenges:
1. TCP Connection Pooling & File Descriptor Leaks: Default HTTP transports restrict concurrent connections per upstream host (`MaxIdleConnsPerHost = 2`), causing excessive socket creation and `TIME_WAIT` saturation under high concurrency. The proxy must implement a tuned custom `http.Transport` with aggressive connection reuse and leak-free response body consumption.
2. Race-Free Dynamic Configuration Reloading: Updating routes and plugin chains via an administrative API while thousands of concurrent requests are executing requires lock-free or copy-on-write atomic memory swapping (`atomic.Pointer`) to prevent data races and dropped client connections.
3. Memory Safety Under Body Transformations: Inspecting and rewriting request or response bodies in middleware plugins breaks HTTP streaming and risks Out-Of-Memory (OOM) crashes unless bounded by explicit memory limiters (`http.MaxBytesReader`).

ARCHITECTURE & DATA FLOW
----------------------------------------
1. Client Request Arrival: Downstream client opens HTTP connection to the gateway entry port (e.g. `:8080`).
2. Route Matching: The request path, method, and host headers are matched against an in-memory radix tree or hash table of active routes.
3. Plugin Chain Execution: The matched route defines an ordered pipeline of plugins (`AuthPlugin` -> `RateLimitPlugin` -> `TransformPlugin`). Each plugin executes sequentially; a rejection aborts the request with appropriate status headers.
4. Upstream Resolution & Load Balancing: The gateway selects an active upstream server from the route's target pool using weighted round-robin or least-connections algorithms, filtering out unhealthy instances identified by background health checks.
5. Reverse Proxy Forwarding: The custom `httputil.ReverseProxy` forwards the request, injecting tracing headers (`X-Forwarded-For`, `X-Request-ID`) and utilizing pooled persistent connections.
6. Response Streaming: Upstream response headers and body stream back to the downstream client with recorded latency metrics exported to Prometheus.
7. Admin Plane: An independent HTTP endpoint (`:8081/admin/routes`) accepts JSON configuration updates, validating and atomically swapping the global routing pointer.

SAFETY AND ETHICS NOTE
----------------------------------------
API Gateways are the front gate to application infrastructure. Vulnerabilities in header sanitization or connection pooling can expose backends to HTTP Request Smuggling, denial-of-service, or authentication bypass. The implementation enforces strict header cleaning (`X-Forwarded-*` validation) and bounds maximum request headers and body sizes.
